# Waiting and Inbox workflows

## Wait on GitHub or try again later

Never poll GitHub in a loop or `sleep` between checks. `tuile --repo <DIR> wait pr <N> --until checks-settled|merged|closed --timeout 30m` checks on a shared cadence (every waiter on that PR shares one request) and prints the last observation as JSON. It exits 0 when the condition holds, 2 when the timeout passes first, and 3 when GitHub cannot be read. Claude Code: run it in the background and end the turn, so its exit wakes you. Codex and Pi: run it in the foreground with a `--timeout` under your command limit, and run it again on 2. For a plain "try again in two minutes", `tuile schedule in 2m -- <command>` has the scheduler run the command once (`schedule list`, `schedule cancel <ID>`). GitHub refusals that start `GitHub is paused` or `GitHub is busy` mean no request was made: wait, then retry, and never work around them. Verify availability with `tuile wait --help` before using an older binary.

## Ask the owner something

**Claude Code:** when the `tuile` MCP server is available, use its `ask_owner` tool (`mcp__tuile__ask_owner`, or `mcp__sbt__ask_owner` where it was added under its old name) instead of `AskUserQuestion` or a question in your wrap-up. It publishes a real Inbox form under your session identity, waits for the owner to send it, and returns their answer. Supply `question`, optionally two short `choices` and a `recommended` choice, and `pictures` or `open` when the question is about something the owner can look at. A `still_waiting` result names a `form_id`: call again with `wait_for` set to that id rather than publishing a duplicate. A timeout is not approval. If the tool is unavailable, use the CLI form flow below; do not mistake a transcript's Needs you bell for an answerable form. The owner can configure access from the repository with `claude mcp add tuile -- tuile mcp` and restart Claude; never change their MCP configuration without permission.

When you need the owner's answer, or want them to test something in the app, publish a form (`tuile form example` gives the schema) instead of asking in chat. Offer two short choices; they can always answer in their own words, which reaches you at once with any other questions unanswered. To A/B images or wireframes, give each choice a `"picture"` (a question takes `"pictures"`), as local PNG, JPEG, GIF or WebP paths; the owner's own pictures come back in the submission's `"pictures"`, in the response's `"picture_folder"`. Set `"open"` to the window page the question is about (`agents`, `wiki`, `tasks`, `analysis`, ...), so its Inbox row takes them there; for charts, `"analysis/<worksheet>"` opens that Analysis worksheet. A question that asks the owner to review, compare or approve something they can look at (charts, a page, a design, a screenshot) carries it on the card: pictures of it you made, `open` set to where it is, or both. Never write "after reviewing the charts" on a card that carries neither, and never ask them to approve something you have not looked at yourself. Set `"task"` to the task it decides and `"done": true` on the choice that finishes it, such as "Nothing's off": sending that answer marks the task done. Then run `tuile --repo <DIR> wait form <ID> --producer <YOU>` in the background and end your turn: it exits when they answer, which wakes you (exit 2 means it timed out, so run it again). After `tuile edit <ID> --add-label ask:owner --append-notes "<the ask>"`, `tuile wait reply <ID>` does the same for a flagged task.

## Put a response in the Inbox

`tuile form example --review` gives the schema. Use a unique `review/...` id and your exact producer identity, one logical point per item, then `tuile --repo <DIR> form publish --file <JSON>`. Read the submission with `form response <FORM_ID> --producer <SESSION_ID>`, then acknowledge its exact submission id with `form ack`. Silence and untouched items never imply approval. A choice question (`single_select`) offers exactly two choices of one or two words each; you pick them, and the owner may answer in their own words instead, which arrives as `{"type":"other","value":"..."}`. When you have a clear answer to a choice question, mark that option `"recommended": true` (one per single_select): once every required question has one, the owner can accept them all in one step.
