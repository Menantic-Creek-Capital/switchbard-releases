# Setup and agent identity

## Setup

`tuile --repo <DIR> doctor --json` reports readiness; it creates nothing. SQLite is embedded. If `tuile` is missing from PATH, help the user find the installation; ask before installing packages or changing shell config. Offer `tuile --repo <DIR> init` for an unconfigured directory (`--yes` only when defaults are authorized); never migrate, reset or delete data to make setup pass. Ask before `doctor --github`; the user completes `gh auth login` themselves, and no token is ever read or printed.

## Who you are to tuile

Live work is **session ownership**: `tuile work claim <ID>` before editing lights the row up and moves the task to In Progress; `tuile work release <ID> --note "What remains, why, next action"` hands it back. Release is not Done. Keep ownership across ordinary replies, questions, pauses and waits for the owner (including sign-in); these are not handbacks. Release only after completed delivery or an explicit handback, not merely to end a turn. Say what is blocked and what action is needed while retaining the claim. `tuile work list` shows other holders; coordinate, never steal a claim. Identity differs by harness:

- **Claude Code**: identity comes from its session and pid env vars; the hooks `tuile harness install` adds to `~/.claude/settings.json` (or a repo's `.claude/settings.json`) call `tuile work hook` to enforce claim-before-edit. Ordinary stops retain ownership without forcing another turn; background waits also retain their recorded wait details. Only an explicit autonomous continuation policy (`--max-stop-blocks` greater than zero) holds stops. End a turn to report progress or await the owner without releasing the claim.
- **Pi**: the tuile extension (`tuile skill install --agent pi`, then `/reload`) supplies identity, gates edits through the same hook, and with pi-subagents installed reports the session's active sub-agents so Processes nests them under the parent row. With `@parke.dev/pi-subagent`, inspect children with `/subagents` and collect background results with `subagent_wait` or `subagent({ action: "wait", id })`. Its `explore` and `review` profiles, which parallel tasks take by default, are read-only with no bash: give a child that must run commands, scripts or queries `profile: "general"` (the tuile extension says so in a Pi agent's system prompt, flag `subagent_profile_hint`). Sub-agents never claim or hold tasks.
- **Codex**: `tuile harness install --agent codex` sets Codex's `notify` to `tuile agent codex-notify`, which reports each finished turn to the Agents page. No claim hooks; claim with explicit `--agent codex --session <ID> --pid <PID>` of the real long-lived process, or use the plain task commands.

To create and grab new work, use `tuile create "Title" --claim` with those same identity exports or explicit flags. It creates In Progress, waiting on the agent; plain `create` stays unclaimed. Identity flags require `--claim`; `--status` conflicts, future snooze is refused, and the PID must be live. If a later claim write fails, stderr names the retained task ID: inspect `work list` and retry `work claim <ID>`, never blindly create again.

## Task execution loop (Pi)

This executes tasks and is separate from tuile's `tuile goal` tracking. `/tuile-execute <ID>` reads and claims the task for the actual Pi session/PID/worktree, then continues automatically at each settlement until release, `/tuile-execute pause` or a real failure; pausing keeps the claim. Reload restores the execution state. Each turn: one bounded step, the repository's required checks, evidence through `tuile edit`, only proved criteria checked. Release **last**, after notes and verification, only for completed delivery or an explicit handback. A progress reply, owner question or sign-in wait must not trigger release; pause execution and retain ownership instead. Escape or errors stop automation without completing or releasing. Tasks are the acceptance contract: no competing goal store, no completion inferred from a model reply, no scope expansion. These are workflow gates, not a sandbox: a repo claim authorizes edits in that worktree, not one task's files, and Working proves ownership, not ongoing model activity or success.
